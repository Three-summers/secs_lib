# SML 易用性增强与演进路线图

> 文档创建日期：2026-01-18
> 状态：提案 (Proposal)

本文档基于对当前 `secs::sml` 架构的深度分析以及对“工业级易用性”的探讨，总结了 SML 模块未来的功能扩展方向。

目前的 SML 实现了**“声明式定义”**和**“运行时匹配”**，解决了“发消息”和“定消息”的问题。下一阶段的演进目标是解决**“收消息”**和**“工程化管理”**的痛点，实现真正的**“配置即解析”**。

## 优先级概览 (Roadmap Priorities)

我们将改进方向分为三个阶段：
*   **P0 (Core Usability)**: 解决核心痛点，大幅减少 C++ 样板代码，改变开发模式。
*   **P1 (Engineering)**: 提升大型项目的可维护性和开发效率。
*   **P2 (Robustness & Integration)**: 增强协议健壮性和与业务逻辑的胶水能力。

| 优先级 | 功能特性 | 核心价值 | 解决痛点 |
| :--- | :--- | :--- | :--- |
| **P0** | **数据捕获 (Data Capture)** | 配置即解析 | 消除 C++ 侧繁琐且脆弱的手动遍历 `Item` 树的代码。 |
| **P0** | **深层路径索引 (Deep Pathing)** | 直观定位 | 支持 `[1][2]` 语法，解决 `(n)` 先序遍历编号反直觉、难维护的问题。 |
| **P1** | **常量定义 (Constants)** | 语义化配置 | 消除魔术数字（如 CEID、状态码），便于统一修改。 |
| **P1** | **文件包含 (Include)** | 模块化复用 | 解决单文件过大问题，支持复用标准消息定义。 |
| **P1** | **CLI 工具链** | 开发反馈 | 提供独立语法检查工具，无需编译 C++ 即可验证 SML。 |
| **P2** | **自动校验 (Auto S9F7)** | 协议健壮性 | 自动拒收结构不匹配的消息，保护业务逻辑不处理脏数据。 |
| **P2** | **上下文自动关联** | 协议正确性 | 自动处理 Request/Reply 的 System Bytes 传递。 |

---

## 详细功能规格

### 1. 数据捕获 (Data Capture) [P0]

**现状**：
目前 SML 仅用于匹配消息类型（如 S6F11），用户收到消息后，仍需在 C++ 中手动编写大量 `get_child()`, `get_value()` 代码来提取数据。一旦 SML 结构变动，C++ 代码极易崩溃。

**建议方案**：
引入捕获变量语法（如 `$VAR`），在匹配的同时自动提取数据。

**SML 语法示例**：
```sml
// 匹配 S6F11，同时将 DATAID, CEID 和 RPTLIST 提取到变量中
if (S6F11 <L [3] <U4 $DATAID> <U4 $CEID> <L $RPTLIST>>) on_event.
```

**C++ 调用变化**：
```cpp
// 现在的写法（痛苦）：
// auto ceid = msg.root->get_child(1)->get_value<U4>();

// 改进后的写法（优雅）：
auto vars = runtime.match_and_capture(msg);
uint32_t ceid = vars.get<uint32_t>("CEID"); // 直接获取
```

**收益**：
实现 SML 与 C++ 的双向绑定，真正做到“修改配置文件无需修改代码逻辑”。

---

### 2. 深层路径索引 (Deep Path Indexing) [P0]

**现状**：
当前 SML 仅支持 `(n)`（1-based 先序遍历编号）或 `[i]`（单层 List 下标）。
对于复杂嵌套消息（如 S6F11 嵌套 List），用户必须人肉计算先序遍历编号（如 `(15)`），极易出错且难以阅读。

**建议方案**：
扩展 AST 和 Parser，支持链式下标访问。

**SML 语法示例**：
```sml
// 选中：根 List 的第 1 个子项 -> 该子项（也是List）的第 2 个子项
if (S6F11[1][2] == <A "Alarm">) handle_alarm.

// 结合命名访问（如未来支持）：
// if (S6F11.RPTLIST[0].ID == 1001) ...
```

**技术实现**：
将 AST 中的 `optional<size_t> list_index` 升级为 `vector<size_t> path`，并在解析时支持循环匹配 `[` `Index` `]`。

---

### 3. 常量与模块化 (Constants & Modularization) [P1]

**现状**：
所有消息定义必须写在一个大字符串或文件中；状态码、CEID 等全是字面量数字。

**建议方案**：
*   **常量**：`const CEID_PROCESS_STATE = 1001.`
*   **包含**：`include "common_defs.sml".`

**SML 语法示例**：
```sml
include "std_constants.sml".

const MY_CEID = 0x200.

// 使用常量
reply: S6F12 <L <U1 ACK_OK> >. // ACK_OK 定义在 std_constants.sml 中
```

---

### 4. 自动校验与异常处理 (Auto-Validation) [P2]

**现状**：
如果对方发送的消息 Stream/Function 匹配，但 Item 结构不对（例如期望 `U4` 收到 `A`），目前的 Runtime 可能会让匹配失败，或者抛给用户处理。

**建议方案**：
Runtime 内置校验逻辑。如果 S/F 匹配但结构不符合 SML 定义，框架自动回复 **S9F7 (Data Illegal)**，并记录错误日志，不再回调业务层。

**收益**：
大幅提升系统的防御性编程能力，确保业务层收到的数据永远是类型安全的。

---

### 总结

当前 SML 已经具备了优秀的“骨架”。为了让其丰满并适应复杂的工业场景，我们将优先推动 **数据捕获** 和 **深层路径索引** 的实现。这将直接改变用户编写 SECS 业务代码的方式，从“繁琐的解析”转向“声明式绑定”。
